## 这是什么

《寒蝉鸣泣之时》（ひぐらしのなく頃に / Higurashi When They Cry）是 07th Expansion 的同人文字冒险游戏，Steam 版分八章发售，官方只有英文与日文。

本项目的目标是把 **PC 中文体验完整搬到安卓**：

- 素材用 07th Mod 的 PS3 高清立绘 / 背景 / 语音 / BGM
- 文本用 ycx-Studios 的简体中文汉化
- 引擎基于 [darwin07 的安卓 Ren'Py 移植版](https://darwin07tachibana.blogspot.com/)
- 最终产出**两个独立 APK**，装上即玩，不需要额外下载资源、不需要联网

出题篇（第 1-4 章）：鬼隐篇、绵流篇、祟杀篇、暇溃篇
解题篇（第 5-8 章）：目明篇、罪灭篇、皆杀篇、祭囃篇

## 它做了什么（移植内容详解）

这是本项目的主体工作量。原始安卓移植包存在大量问题，本项目逐个排查并修复：

### 一、文本层

1. **三语语料对齐**
   从 Steam 版脚本提取「日文原文 / 英文译文 / 官方中文」三语对齐语料（`work/corpus/ch1-8.json`，共 11 万余条）。这是后续所有翻译工作的基础。

2. **全量台词中文注入**
   移植包的 `.rpy` 脚本是英文的。逐行替换为中文，包括：
   - 主对话行（`n` / `r` / 各角色 `a_xxx`）
   - `extend` 续行（同一句话被拆成多行时，必须逐行对应）
   - **语音匹配变体台词（vm 组）**——这是最大的坑。07th Mod 的脚本用「语音匹配等级 0-5」来切换不同版本的台词，同一句对话有 2-6 个变体分支（`vm_xxx_00_n01` / `vm_xxx_0x_n01` 等）。移植时这些变体组**完全没有被注入**，导致把设置里的语音等级调高后大量台词变回英文。本项目全部注入并逐句对齐。

3. **% 转义修复（崩溃级）**
   原版脚本里有 `%%` 转义（Ren'Py 字符串格式化用），中文注入时丢失了 `%%`，导致罪灭篇开头直接崩溃（`unsupported format character`）。全项目 28 行修复，并接入构建管线（`fix_percent_escape.py`），以后新增翻译自动免疫。

4. **诗卡 / 黑底白字卡片重绘**
   游戏里大量「黑底白字」的文字是**烤在图片里**的（小章节开场卡、日期地点卡、伯恩卡斯特尔诗、诗音的笔记本页、鹰野独白、祭囃篇闪卡等）。这类文字 OCR 擦不干净会留残影。
   本项目写了 `gen_text_cards.py`：逐图识别原文 → 翻译 → 用原版同款衬线字体重新排版 → 按背景亮度自适应擦除旧字。共重绘 **104 张 + 87 张**卡片，并解决了「文字溢出画布被裁」「抗锯齿灰边残留」「误擦美术」三个问题。

5. **罪灭篇 2600 行补译**
   罪灭篇在源移植包里大段未翻译。直接用单行查表全部失败——根因是 PC 英文脚本与官方中文语料的**行序不一致**（同一句被折成不同的行数）。
   解决方案：用 `difflib.SequenceMatcher` 对**整个篇章的英文台词序列**与语料序列做全局对齐，命中 2612 行；剩余含内联标签（`{w=}` / `{cps=}`）的 69 行由 AI 逐条对照日文原文精修。

6. **界面文案全汉化**
   - 章节跳转按钮 **78 条**（目明篇 26 个场景名、罪灭/皆杀 Chapter 1-26、皆杀 28 个场景名、碎片名等）
   - 音乐室 UI **17 条** + 曲名 **90 条**
   - 存档章节名 **123 处**（此前只有篇名有译，`"目明篇\n"` 这种带换行的整串没登记，存档界面一直显示英文）
   - 说话者名 **246 个**（含组合名，如「圭一＆蕾娜＆沙都子」，带角色专属配色）
   - Tips 标题 127 条（取自 ycx 汉化补丁 DLL 内嵌的官方中文标题）

### 二、素材层

7. **缺图兜底机制**
   移植包引用了约 27 张根本不存在的图片，运行时会显示刺眼的红色 `Image not found` 文字。
   本项目在 `zz_runtime.rpy` 里 hook 了 `renpy.display.image.ImageReference.find_target`，任何未知图像自动降级为深灰块并写日志，界面上永不出现红字。

8. **立绘版本甄别**
   07th Mod 提供三套立绘可切换（萌绘高清 / Steam 版 / 龙绘原版）。本项目统一使用**萌绘（PS3 高清）**版，全部 1280×720，命名体系与 PC 版 `CG/sprite`（2560×1440）一致（降采样）。

### 三、运行时层

9. **视频软解（OP 无法播放的根因）**
   Android 上 Ren'Py 默认 `hw_video = True`，与全屏视频冲突会直接抛异常。改为 `False`（软解），并把视频文件在 APK 内改为**不压缩存储**（STORED）以保证 seek/decode 可靠。

10. **{vw} 标签崩溃修复**
    07th Mod 的 PC 脚本里 `{vw}`（等语音结束）是自注册标签，移植版引擎没注册。任何带 `{vw}` 的台词一渲染就抛 `Unknown text tag` 弹错误页——出题篇 26 处、解题篇 59 处。
    注意：Ren'Py 7.3.5 的自闭合回调签名是 `func(tag, value)`（两参数），不是新版的三/四参数。

11. **OP 播放机制重做**
    - **pending 标记机制**：从菜单/章节选择开新档时写入待播标记，走到章节内锚点时消费。效果是每次开新档都播 OP，读档/跳关不播，播完回滚再前进不重复。
    - **锚点逐章对齐 PC 版**：全部 8 章的 OP 位置对齐到「序章结束、Day 1 尚未开始」的黑屏边界（与 PC 的 `ModCallScriptSection("&opening")` 同位）。
    - **0.9 秒起步保护 + 手点可跳过**：吞掉快进末尾残留的点击，之后任意点击可跳过。
    - **音频声道暂停而非停止**：OP 期间暂停 music/ambient/voice 等 14 个声道，播完原曲从暂停位置继续（不是销毁重载）。
    - **快进/自动到 OP 处自动关闭**。

12. **切后台策略**
    旧策略是「切后台 → 存盘 → 杀进程」，回来要冷启动重载 2 GB 资源（9-10 秒纯黑）。改为 `quit_on_mobile_background = False`：保留进程、回来秒恢复；引擎仍会在切后台时存 `_reload-1` 兜底。另加「后台回来后清掉遗留的快进/自动标记」的清理逻辑（用时间戳判断，不干扰玩家主动快进）。

### 四、音频层

13. **解题篇语音缺口补齐（19182 个 / 908 MB）**
    这是本项目发现的最大素材缺陷。darwin07 的解题篇移植包**完全没有皆杀（s12）和祭囃（s13）两章的 PS3 语音**：

    | 章节 | PC 版应有 | 移植包实际 |
    |---|---|---|
    | s12 皆杀 | 9174 | **0** |
    | s13 祭囃 | 7358 | **1** |
    | s14 | 381 | 0 |
    | s20 | 2463 | 298 |

    本项目的最终交付版从 PC 版第 7/8 章逐个核对补齐，路径与格式完全一致（Ogg Vorbis / 2 声道 / 44100 Hz / 160 kbps），**未做任何转码，保留原始音质**。

    > 体积说明：出题篇 1.92 GB、解题篇 2.75 GB，差的 900 兆全部来自补入的语音。补语音前两个包看起来一样大，是因为「解题篇缺语音（−376 MB）」和「解题篇素材更多（+328 MB 音乐/背景/CG）」两个独立缺陷恰好抵消，是个假象。

14. **出题篇语音补齐**
    出题篇有 15 处语音缺失，其中 9 个 PC 版其实有（已补）；剩下 6 个 PC 版全部 8 章都没有，属官方为规避审查删掉的敏感台词。

15. **音频当图像的致命错误**
    `zz_fix.rpy` 里有 4 条兜底把 `mina3/4/6/7` 指向了 `.ogg` 音频文件——音频当图像用，走到该分支立刻抛异常。改为黑块。

### 五、翻译质量治理

16. **严格判据的错位检测**
    自动补译（尤其是 difflib 序列对齐）会产生「译文错误重复上一行」的缺陷。本项目建立了严格判据：
    只有当「某行中文与**相邻行**的官方译文相似度 > 0.90，且与**本行** < 0.35」时，才判定为错位。
    这个判据可以把「意译」和「错位」区分开——避免了大量误改。
    最终清理：105 处重复缺陷 + 4 处整段错位（含一处语义反转 `I was never their friend` 被译成「我坚信着」）。

17. **一轮完整审计工具链**
    仓库 `src/scripts/` 里有 100+ 个 `zz_*.py` 审计脚本，覆盖：
    - `call/jump` 目标完整性（缺目标在安卓上会直接杀进程）
    - 未知文本标签（渲染即崩）
    - 图像可解析性（严格前缀元组匹配 + 可达性判断）
    - 音频/语音引用存在性
    - 未翻译 say 行
    - 引号配平 / 续行缩进
    - 存档名 `__()` 覆盖率
    - 译文错位 / 重复 / 连续同文段
    - APK 内容与工程 `.rpyc` 的 CRC 一致性

## 技术实现

### 引擎与工具链

| 组件 | 版本 / 说明 |
|---|---|
| 引擎 | Ren'Py 7.3.5.606（Python 2.7） |
| 基础移植包 | [darwin07](https://darwin07tachibana.blogspot.com/) 的安卓移植（`higurashi_android_118.apk` / `higu-kai-android-204.apk`） |
| 反编译 | unrpyc 2.0.3（`.rpyc` → `.rpy`） |
| 签名 | uber-apk-signer 1.3.0（v1 + v2 + v3） |
| 字体 | Noto Sans CJK SC / Noto Serif CJK SC |

### APK 重打包（`build_apk.py`）

不用 apktool，而是**逐条原始字节复制**：

- 遍历原 APK 的每个条目，直接读原始压缩数据写回（保留原 CRC、时间戳）
- 替换/新增的条目按需重压缩（`.rpyc` 用 deflate，`.ogv` 用 **STORED** 不压缩）
- 对所有 STORED 条目做 4 字节对齐（zipalign 等价，保证 `resources.arsc` 在新系统上有效）
- 重写中央目录 + EOCD
- 调用 uber-apk-signer 签名（同一密钥，可覆盖安装升级）

> 超过 2 GB 的 APK 会跳过 signer 内置的 zipalign（32 位索引限制），因为 rebuild 阶段已自带对齐。

### 构建期强制校验（防复发）

这轮踩过一个致命坑：出题篇曾因为 `zz_op.rpyc` 没被写进 APK 而「选章节直接闪退」——`screens.rpy` 把章节入口改成了 `Start('zz_op_onik')`，但目标标签文件不在包里，Ren'Py 找不到 label 时会直接杀进程。

`build_apk.py` 现在含三重校验：
1. `zz_op.rpyc` 必须在待注入文件列表里
2. 扫描 `screens.rpy` 里所有 `Start('xxx')` 目标，逐个确认工程里有对应 `label`
3. 打包完成后再次检查最终 APK 包里 `assets/x-game/x-zz_op.rpyc` 是否存在

任一条不通过立即 `SystemExit` 中止构建。

## 关于 AI 移植

**这个项目全程由 AI 完成移植，没有人工编写代码。**

- **GLM 5 亿 token** — 2026-10-24 免费额度，承担主体工作量：管线搭建、语料对齐、245 个 `.rpy` 文件的注入、审计工具编写、缺陷排查与修复
- **DeepSeek V4.1 Flash** — 协作完成：翻译精修（逐条对照日文原文改译）、代码细节修正、长上下文的批量核对

**人工参与的部分**：
- 设备实机测试与反馈（「选章节闪退」「切后台黑屏」「黑底白字有残字」等问题都是用户实测发现的）
- 提供正版游戏与汉化补丁
- 决策取舍（例如：语音要不要压缩 → 决定不压缩保留原始音质）

**AI 移植的做法**：不是「一键转换」，而是「写工具 → 跑全量 → 静态审计 → 逐条核实 → 修 → 再审计」的循环。整个项目过程中共创建了 100+ 个审计脚本来验证每一步的正确性。这个过程本身也暴露了 AI 的弱点——期间有多次自查误判（例如把「不可达的死代码分支」误判成「会显示黑块的缺陷」、把「意译」误判成「错位」），最终靠更严格的判据兜住了。

**代码与文本的边界**：本仓库只放**移植管线源码**（Python 脚本 + 自定义 `.rpy` 运行时/界面文件）。游戏本身的剧本、美术、音乐、语音均不在仓库内——它们是各自权利人的资产，通过网盘分发成品 APK。

## 用户反馈修复（v18 出题篇 / v17 解题篇）

三个实机测试反馈的问题，根因与修法：

| 问题 | 根因 | 修复 |
|---|---|---|
| 圭一台词段落语音缺失 | `vm_level ≤ 3` 走 PC 原版文本分支（`_00_n01`），该分支原本没移植 PS3 语音 | 核对 PC 正版脚本后补齐 79 处 `voice`（37 处工程已有 + 42 处从 `voice/org/` 逐字节复制，MD5 全一致）；跳过 108 处官方未配；删除 2 处配错变体的语音 |
| 台词句子截断 | 英文被 `{w=}`/`{cps=}` 分段，中文只译了第一段 | 三轮修复共 **281 处**（详见下节）；最后一轮改以 PC 正版为权威对照，复扫后剩 0 条 |
| 回顾界面不自动滚到底 | `yinitial readback_yvalue` 被用户滚动改写成整数像素值并永久保留 | 改为 `yinitial 1.0`；查 `viewport.py` 确认 `event()` 收到输入即清空 `yoffset`，所以打开到底且仍可上滚 |

### 截断修复的三个阶段（这部分值得记一笔）

**第一轮**：用「文本字数 ÷ 语音时长」算字/秒（正常中文配音 3-8 字/秒），全工程 25449 条扫出 426 处，修了 376 处。

**第二轮**：剩下的按英文原文重新分级，发现其中 15 条是误报（英文本身就是短句）。用 `renpy dialogue` 导出引擎实际解析后的文本复核，又抓出 2 处漏修。

**第三轮（关键）**：意识到前两轮的对照源是**移植包里的英文反编译稿**——那是二手移植产物，本身就可能缺内容。改从 PC 正版 `.mg` 直接重建四语对照库：

- 正版 `.mg` 每句同时含**日文原文 + 英文译文**（`CompiledScripts` / `CompiledUpdateScripts`），中文版 `CompiledChineseScripts` 含**官方中文**，另有 `PlayVoice` 操作给出语音文件名
- 重建后 123767 条，比旧语料多 328 条，增量集中在 ch8 两个文件（旧库按 txt 对齐时整段丢掉了）
- 用 `voice` 文件名做对齐键，58567 条 voice 里对齐到 55014 条（93.93%）
- 判据：把 PC 原版同一语音覆盖的**连续记录**拼成完整句，与工程现有文本比长度

**边界规则是这一步的核心难点**。PC 版一句话常被拆成多个 `OutputLine`，只有第一条带 voice。如果按「收集到下一条带 voice 为止」，会把后面的旁白整段吞进来（最初因此虚高 2329 条）。正确的三重终止条件：

1. 日文以**全角空格** `\u3000` 开头 → 是旁白，停
2. 上一句日文以 `」` 或 `"` 结尾 → 一句已闭合，停
3. 中文以收引号结尾 → 这句已说完，停

按此规则确认 **281 条真截断**（205 HIGH + 76 MID），全部用 PC 官方中文补全，并按英文原文的标签位置重排 `{w=}` / `{cps=}` / `{b}`。

修完复扫：HIGH 240→36，MID 118→0；36 条逐条核实后确认全是误报，**实际剩 0 条**。

**踩过的坑**：批量拼装时语料里的引号会变成屏幕上的多余双引号（`onik_014_02` 那句「对不起」重复了 4 次）；`{b}` 标签跨行未闭合会让后文一直粗体；还有一处语义错得离谱——接待员复述客人姓名「前原…前原。」被补成了第一人称「我是前原」。这些都是复核阶段抓出来的。
